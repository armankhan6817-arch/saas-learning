Three Ways to Reach Supabase

Week 6 reference: loading and saving data from a Next.js page.

The examples use a made-up books table (id, title, created_at), not your notes table. That's on purpose: you still have to translate each example to notes / content yourself, which keeps the typing rule intact. Read the examples, don't copy them.
A. Library in the page B. API route C. Raw fetch Comparison

What's the same in all three

However your code reaches Supabase, it ends up as the same HTTP request to the same address:

https://<your-project>.supabase.co/rest/v1/books

Supabase automatically creates this web API (called PostgREST) for every table you create. Every request goes through the same checks:

  1. Does it carry a valid key? If not, it's rejected straight away.
  2. Which role does the key stand for? The publishable key = anon.
  3. What do the RLS policies allow that role to do? Rows it isn't allowed to touch are silently left out.
  4. The query runs in Postgres, and the rows come back as JSON.

So the three methods only differ in who builds that request and where it's sent from: the user's browser, or your server.

A. The supabase-js library, called from the page

Browser: page.js
   │  supabase.from("books").select(...)
   ▼
supabase-js builds the URL + adds the key header
   │  HTTP GET  /rest/v1/books?select=...
   ▼
Supabase ── checks key → role anon → RLS ──► books table
   │
   ◄──────────── { data, error } ──────────────┘

Files involved

  • lib/supabase.js: creates the client once (you've already written this).
  • app/page.js: "use client", and it calls the client directly.

Loading

async function loadBooks() {
  const { data, error } = await supabase
    .from("books")
    .select("id, title, created_at")
    .order("created_at", { ascending: false });

  console.log(data, error);
}
  1. async function loadBooks(): a function you can use await inside. You'd declare it and call it inside a useEffect, so it runs once when the page opens.
  2. supabase.from("books"): which table. Like SQL's FROM books.
  3. .select("id, title, created_at"): which columns, like SQL's SELECT. Column names go in one string, separated by commas.
  4. .order("created_at", { ascending: false }): like ORDER BY created_at DESC.
  5. await: the chain only describes the query. await actually sends it and waits for the reply.
  6. const { data, error } = ...: destructuring. The library never throws for database errors; it always returns this object:
    • success → data = array of rows, error = null
    • failure → data = null, error = object with a .message
    • RLS blocked it → data = [], error = null (the silent case from your mistakes log)

Saving

const { error } = await supabase
  .from("books")
  .insert({ title: newTitle });
  1. .insert({ title: newTitle }): like SQL's INSERT INTO books (title) VALUES (...). The object's keys must match column names exactly. You don't send id or created_at, because the database fills those in (identity column, default now()).
  2. Only error is useful here. By default, insert doesn't send the new row back. After saving, either call loadBooks() again, or chain .select() after .insert(...) to get the saved row back.

Pros

  • Least code: one file, no URL strings, no headers.
  • The query chain reads like your SQL.
  • Handles errors consistently: always { data, error }.
  • Week 7 login is easiest here: the library stores the logged-in user's session and sends it with every request automatically, so RLS knows who's asking.
  • It's how the official Supabase docs do it, so answers you find online match your code.

Cons

  • The key and project URL are visible in the browser. That's fine by design, but all your security then depends on RLS. One wrong policy means a data leak.
  • Hides the HTTP underneath, so you learn less about how the web works.
  • Nowhere to put server-side rules like "max 500 characters" or "max 20 notes per minute". A user can call Supabase directly and skip your page's checks.
  • Adds a library to the JavaScript the browser has to download.

B. An API route in between (the Week 5 pattern)

Browser: page.js
   │  fetch("/api/books")
   ▼
Your server: app/api/books/route.js   (runs on Vercel, never in the browser)
   │  supabase.from("books").select(...)
   ▼
Supabase ── checks key → role → RLS ──► books table
   │
   ◄── { data, error } ── route.js ── Response.json(...) ──► page.js

Files involved

  • lib/supabase.js: the same client as in A.
  • app/api/books/route.js: the server side. The folder path becomes the URL /api/books.
  • app/page.js: only does fetch("/api/books"). It never touches Supabase.

Server side: app/api/books/route.js

import { supabase } from "@/lib/supabase";

export async function GET() {
  const { data, error } = await supabase
    .from("books")
    .select("id, title, created_at")
    .order("created_at", { ascending: false });

  if (error) {
    return Response.json({ error: error.message }, { status: 500 });
  }
  return Response.json(data);
}
  1. export async function GET(): Next.js calls this when a GET request hits /api/books. A plain fetch(url) is a GET. Tonewriter used POST because the page was sending text.
  2. The query is exactly the same as in A. It just runs on the server now.
  3. if (error): turns a database failure into a real HTTP error. status: 500 means "the server broke", so the page's res.ok check will catch it. (Your 09-08 log entry: no status = defaults to 200 = the failure looks like success.)
  4. Response.json(data): a shortcut for new Response(JSON.stringify(data), { headers: {"Content-Type": "application/json"} }).

Page side: app/page.js

async function loadBooks() {
  const res = await fetch("/api/books");
  if (!res.ok) throw new Error("Request failed: " + res.status);
  const books = await res.json();
  console.log(books);
}
  1. fetch("/api/books"): a relative URL, so it goes to your own site, not Supabase.
  2. if (!res.ok): check the status before .json(). If the route doesn't exist, you get a 404 HTML page, and .json() would crash trying to parse it.
  3. await res.json(): turns the response body back into a JavaScript array.
  4. This also goes inside a useEffect. Calling fetch directly in the component body runs it on every render.

Saving works the same way: an export async function POST(request) in the route reads the body with await request.json() and calls .insert(...). The page sends fetch("/api/books", { method: "POST", headers, body: JSON.stringify(...) }), the same shape as Tonewriter.

Pros

  • Can use secret keys: code in route.js never reaches the browser. That's why Tonewriter needed it for the Claude key.
  • Rules users can't skip: validate length, block empty notes, rate-limit, reshape the data, and call other APIs (like Claude) in the same request.
  • The browser only ever sees /api/books. It never learns your Supabase URL or table names.
  • A pattern you already know from Week 5.

Cons

  • Two files and twice the error handling: check error in the route and res.ok in the page.
  • An extra hop: browser → your server → Supabase → your server → browser. Slower.
  • Each call runs a Vercel serverless function, which counts toward free-tier limits and can be slow the first time (a "cold start").
  • Login gets harder (Week 7): the route has to find out who the user is, usually from cookies with the @supabase/ssr package. That's a lot more setup than in A.
  • Trap: if you put the secret/service_role key in the route, RLS is ignored. Then you're responsible for all the security yourself.

C. Raw fetch straight to Supabase's REST API

Browser: page.js
   │  fetch("https://<project>.supabase.co/rest/v1/books?select=...",
   │        { headers: { apikey: KEY } })
   ▼
Supabase ── checks key → role anon → RLS ──► books table
   │
   ◄────────── JSON array (or an error JSON) ─────┘

This is exactly what supabase-js does for you in method A, done by hand. No library, no route.

Files involved

  • app/page.js only. You don't even need lib/supabase.js, just the two values from .env.local.

Loading

async function loadBooks() {
  const url = process.env.NEXT_PUBLIC_SUPABASE_URL
    + "/rest/v1/books?select=id,title,created_at&order=created_at.desc";

  const res = await fetch(url, {
    headers: { apikey: process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY },
  });

  if (!res.ok) {
    const err = await res.json();
    throw new Error(err.message);
  }
  const books = await res.json();
  console.log(books);
}
  1. The URL is the query. After ?, each name=value pair is one part of the SQL, joined with &:
    • select=id,title,created_at → SELECT id, title, created_at (commas, no spaces)
    • order=created_at.desc → ORDER BY created_at DESC
    • you could add &limit=3 → LIMIT 3
  2. headers: { apikey: ... }: the key travels in a header, not in the URL. Without it, Supabase answers with an error and a 401 status. (With an older eyJ... anon key, if you still get 401, also send Authorization: "Bearer " + key. The new sb_publishable_ key works with apikey alone.)
  3. if (!res.ok): you have to catch errors yourself. Supabase sends the error details as JSON with a message property.
  4. await res.json(): on success, the body is a plain array of rows, with no { data, error } wrapper. That wrapper is something supabase-js adds.
  5. This also goes inside a useEffect.

Saving

const res = await fetch(process.env.NEXT_PUBLIC_SUPABASE_URL + "/rest/v1/books", {
  method: "POST",
  headers: {
    apikey: process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ title: newTitle }),
});
  1. method: "POST" on the table's address = INSERT.
  2. "Content-Type": "application/json": tells Supabase the body is JSON, the same as in Tonewriter.
  3. body: JSON.stringify(...): the new row, converted to text.
  4. On success Supabase replies 201 Created with an empty body, so don't call .json() on it. If you want the saved row back, add the header Prefer: "return=representation".

Pros

  • Best for learning: you can see the real HTTP request (URL, method, headers, status codes). After this, supabase-js stops being magic.
  • No library to download, and no route file.
  • Uses only fetch, which you already know from Weeks 3 and 5.

Cons

  • Building URLs by hand is fragile: one typo (a space after a comma, order=created_at desc) and you get an error or wrong results. Filter values with special characters need encoding.
  • Headers on every request, error handling on every request, and special cases to remember (empty 201 body, Prefer header).
  • Login is painful (Week 7): you'd have to attach the user's token to every request and refresh it before it expires. The library does all of that for you.
  • It has the same security model as A: the key is in the browser, and RLS does all the protecting.
  • Almost nobody writes real apps this way, so you'll find few examples to learn from.

Which to use when

  • Quick Notes (this week): A. It's the least code, and it prepares you for Week 7.
  • Do C once as a 15-minute exercise: load notes with raw fetch, look at the request in DevTools → Network, then switch to A. You'll understand what the library is doing.
  • Use B when you need something the browser must not have: a secret key (Claude, payments), rules users can't skip, or several services called in one request. In Week 9's app (AI + auth + DB), the Claude call goes through a route, and the plain data reads can still use A.
